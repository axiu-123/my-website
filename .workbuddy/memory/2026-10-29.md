## Bugfix：高级模式只有第一段能播放 / 后续生成无声
- 症状：第②步三段片段只能听第一段，其余放不出；听完后第③/④步「完成作曲」也无声。
- 初次修复（position=0）无效：原判 `Tone.Transport` 播放头未归零，`startPlayback` 加 `stop/cancel/position=0`，用户实测仍只有第一段响 → 说明根因是全局 Transport 反复 stop/cancel/start 的状态机本身不稳定，scheduleOnce 排程时间不可靠。
- 最终修复（已生效）：实时播放彻底抛弃全局 Transport，改 `playEvents()` 用 `Tone.now() + 0.06` 绝对音频时间给每条音符独立调度；每个片段独立 `makeInstruments` 实例 + 独立时间起点，互不干扰。第④步成曲、基础模式、片段试听全部走此路径。`Tone.Transport` 仅保留给 `Tone.Offline` 导出 WAV（其自带独立 Transport）。
- 已部署并 curl 验证线上 `/compose/app.js` 含 `playEvents`/`Tone.now()`，旧 `Transport.position` 已消失。
- 注：用户反馈「刷新后网页打不开」= Render 免费版休眠冷启动（约 30–50s 唤醒），非代码问题。

## Bugfix 2：片段试听/停止仍失效的真正根因（async/await 调用 bug）
- 症状（用户二次反馈）：三段仍只有第一段响、第一段不能停止、第③步「改片段」消失。
- 真正根因：`startPlayback` 是 async 函数、返回 Promise，但调用处写 `preview = startPlayback(...)`（未 await），使 preview 变成 Promise 而非 {stop} 对象。`stopPreview/stopLive` 调 `preview.stop()` → TypeError 抛异常 → 第2/3段试听 handler 中断（startPlayback 未执行）不响；停止按钮同样抛错失效；异常也波及第③步渲染。前两次的 position=0、playEvents 只是音频机制层修复，未触达此调用 bug。
- 修复：①两处片段试听按钮 handler 改 `async () => { ... preview = await startPlayback(...) }`；②stopLive/stopPreview 加 try/catch 防御；③renderStep3 空选时 fallback 到 [0]；④startPlayback 内部开头先 stopLive()/stopPreview() 防快速连点双声。
- 部署波折：GitHub 内容早已最新（sha 19a33198 含 2 处 await），但 Render auto-deploy webhook 在 502 抖动时未触发；重新推送一次触发 Render 重新部署，curl 验证线上 await 数=2，确认生效。
